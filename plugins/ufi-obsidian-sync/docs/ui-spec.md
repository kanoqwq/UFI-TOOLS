# UFI Sync Node 2.3 开放产品化规格

## 目标

把当前已验证可用的个人插件整理为任何 UFI-TOOLS 用户都能配置的 Obsidian
同步产品，同时降低 device 上同步内核的峰值内存和空闲管理负载。

## 用户界面

- 新安装不得包含开发者或现有用户的仓库、设备 ID、路径和名称。
- 未完成配置时显示首次设置引导；已有配置的升级用户直接进入状态台。
- 日常首屏只回答：device 副本是否最新、多少台电脑在线、是否有待同步数据、
  是否需要用户处理。
- 主操作为“立即同步”和状态相关的“启动/继续设置”；仓库、电脑和维护动作进入二级区域。
- 配置区采用三步结构：添加 Obsidian 笔记库、添加电脑、检查并应用。
- “保存并应用”一次完成保存、重新生成托管配置、重启和状态刷新；普通用户
  不再手工执行“保存 → 初始化 → 重启”。
- 可复制 device 设备 ID，并明确提示用户仍需在电脑端添加 device、共享相同 Folder ID。
- 界面使用通用“电脑/设备”语言，不写死 Mac 或 Windows；支持合法的
  Mac、Windows、Linux 或其它 Syncthing Device ID。
- 不用“同步完成”推断远端电脑也已拿到文件。device 本地 `needBytes=0` 时表述为
  “device 已保存最新副本”；电脑离线不是错误。
- Syncthing 版本、PID、端口、证书、root、原始日志只在技术维护区显示。
- 320px 窄屏保持单列、不产生横向滚动；状态不能只依赖颜色表达。

## 配置兼容性

- 保留现有 `F|id|label` 与 `D|id|label` 格式。
- 已存在的 `sync.conf` 不迁移、不删除、不替换。
- 52 位旧式 Device ID 在用户重新应用配置时补齐官方校验位；设备身份与名称不变，
  损坏或重复的历史 ID 必须在写入设备前拒绝。
- 仅当配置文件不存在时创建空文件；保存时仍要求至少一个仓库和一台电脑。
- 本轮继续采用“每台已配置电脑共享全部已配置仓库”的模型；逐仓库权限矩阵
  和普通文件夹配置档不在本轮范围。
- 删除配置项不会删除 device 或电脑中的数据；删除 device 副本仍是独立危险操作。

## 低资源运行

- 使用 Syncthing 1.30.0 官方低资源建议：`databaseTuning=small`、
  `maxFolderConcurrency=1`、`maxConcurrentIncomingRequestKiB=32768`。
- 每个仓库使用单 copier、单 hasher、16 MiB pending buffer，并关闭扫描进度统计。
- 每台电脑只建立一个 Syncthing 连接。
- 启动环境使用可覆盖的软内存预算和较积极 GC；默认值必须兼顾约 1 GB
  Obsidian 仓库的正常同步，不能通过禁用 fsync 或 TLS 换取资源数字。
- device 外部看门狗负责故障恢复；`STNORESTART=1` 只关闭 Syncthing
  monitor 的内部重启，不会消除 monitor 进程。不依赖隐藏的 `STMONITORED`
  开关；重启后必须重新验证在线设备、中继、仓库完成度与“立即同步”。
- 状态输出沿 PID 文件指向的受管进程树统计合计 RSS、进程数和线程数，不在高频轮询中
  全量扫描 `/proc` 或反复启动 `syncthing --version`。PID 恢复扫描命中后要原子修复 PID 文件。
- 前端轮询自适应：同步/异常时较快，健康空闲时较慢，折叠时 60 秒，页面隐藏时暂停；
  任意时刻最多一个状态请求。
- 配置和状态 DOM 只在内容变化时更新，日志输出保持有界。

## 必须通过的行为测试

1. 新安装首次读取为空配置，不出现任何个人设备 ID或预置仓库。
2. 任意合法 Folder ID、中文名称和第三台虚构主机可以添加、保存、生成 XML。
3. 小写、无连字符 Device ID 被规范化；重复、非法和注入式输入被拒绝。
4. 单击“保存并应用”先部署当前控制脚本，再严格执行
   `set-config → apply-config → status`；设备端先生成并验证候选 XML，再原子切换和启动，
   事务锁期间看门狗不介入；失败时恢复原 `sync.conf/config.xml` 与原运行状态，不宣称成功。
5. 旧配置解析、展示和重新应用后设备身份与名称不变；52 位表示可正规化为 56 位表示。
6. 空配置不允许初始化同步，但允许安装内核和继续设置。
7. 生成的 XML 包含全部低资源参数、动态地址和公网中继，且仍为 `receiveonly`。
8. UI 不把 device 本地完成误写成所有电脑完成；断线电脑及时显示离线；状态请求失败或区块缺失时显示未知，不沿用在线、百分比或 0 B。
9. 100 次状态渲染不增加按钮、计时器或日志节点；轮询不会并发。
10. 构建、Shell/JS 语法、设备逻辑、运行环境、看门狗、立即同步和产物一致性测试全部通过。
11. 安装包必须与插件内置的 1.30.0 可信 SHA256 一致；其它版本、缺少可用 SHA256 工具或哈希不一致时必须失败关闭，不把设备端 SHA256 检查表述为 PGP 验签。
12. `.` / `..` Folder ID 在前后端都被拒绝；历史恶意配置不能使删除动作越出仓库根目录。
13. 点“停止”后看门狗与开机脚本保持停用；显式启动会清理停用标记。
14. 安装后持久保留 Syncthing MPL-2.0 LICENSE，发布树包含第三方声明。
15. 安装任务必须原子互斥：活任务拒绝并发；超时任务只有在核验所有者身份、进程启动标识
    并确认其下载子进程全部退出后才能接管；成功、失败和信号中断都释放锁。
16. 重装或升级保留已有 `config.xml` 的同步端口，缺失时才回退 `state.env`；只有全新安装
    才探测空闲端口。已有内核缺少 LICENSE 时可离线、校验后原子补齐，不重新下载内核。
17. 控制脚本部署必须先验证随机候选文件再原子替换；升级下载、校验或启动失败时恢复旧内核
    与原运行状态；停止失败和危险动作的空/失败响应不得在 UI 中显示成功。
18. 旧 52 位 Device ID 在尚未重新保存时也必须先规范化再查询连接状态；`db/status` 的空对象
    或缺少字节字段必须显示未知。本地 REST 单次最多 2 秒，最大 20 库时前端总调用不超过
    UFI-TOOLS 的 60 秒上限，且仍保持单飞。
19. 同步内核在线升级在改成后台任务 + 状态轮询、并验证宿主中断回滚前不得暴露 UI 按钮；
    当前面板固定安装/修复可信白名单中的 1.30.0。

## 真机验收

- 在不改动现有仓库和设备 ID 的前提下升级设备脚本并重启。
- 两个既有仓库仍为 100%，Mac/Windows 连接能力不回退。
- 记录升级前后空闲 RSS；确认状态能展示 RSS，且新配置包含低资源参数。
- 若设备已在记录基线前完成升级，只报告升级后实测值并明确“升级前基线缺失”，不得推算降幅。
- 若需要测试第三台真实主机，应使用独立临时仓库，不能把虚构 ID 应用到当前生产配置。

## 公开发布门槛

- 发布目录不得包含真实 Device ID、个人路径、局域网地址或生产仓库预置值。
- README 必须说明同步副本不是历史备份、跨网状态的真实含义、默认忽略项和自动回滚边界。
- Syncthing 的来源与 MPL-2.0 归属必须保留；设备上要保留发布包 LICENSE，源码树要有第三方声明。插件自身许可证由作者明确决定，未决定前不得把源码仓库标记为开源发行版。
- macOS 与 Windows 真机链路已验证；Linux 或其它第三平台的真实端到端连接仍是正式推广前
  的建议验收项，自动化三主机 XML 测试不能冒充真机联网结果。
- 当前共享暂存文件的保存协议只支持一个管理页面提交配置。正式公开发行前建议改为独立
  事务 ID + 配置 revision 的原子提交和冲突检测；完成前必须把“不要多标签页同时保存”写入说明。
